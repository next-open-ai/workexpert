# 架构与契约

> 状态：实施中｜规格版本：0.1｜更新日期：2026-09-23

## 检索链路

```text
用户问题
  ├─ 原问题向量召回（保底）
  └─ 本体查询规划
       ├─ 实体/别名归一化
       ├─ 一跳关系扩展
       ├─ 增强查询
       └─ 文档与来源提示
              ↓
        增强向量召回
              ↓
候选合并、去重、图谱提示加权
              ↓
后续：权限/时效/版本过滤与 reranker
              ↓
大模型基于证据回答
```

图谱不是正文仓库。节点和关系负责表达“是什么、与谁有关、去哪找”；知识库切片负责提供可引用原文。

## 数据模型

- `OntologyNode`：`id/type/name/aliases/properties/source/status`；
- `OntologyEdge`：`subjectId/predicate/objectId/properties/source/status`；
- `OntologyGraph`：版本化节点和关系集合；
- `OntologyQueryPlan`：匹配节点、相关节点、关系、扩展词和过滤提示。

第一阶段按知识库数据目录保存 `ontology.sqlite`，由 sql.js 操作。节点、关系、候选、元数据和发布版本分别落在关系表中；本地切片仍由 LanceDB 或现有文件回退存储。二者通过 `documentId`、`source` 等稳定引用关联。旧版 `ontology.json` / `ontology-workflow.json` 会在首次打开时单向导入 SQLite，原文件保留作回滚备份。

## API

| API | 作用 |
| --- | --- |
| `POST /api/knowledge/ontology/replace` | 校验并整体替换图谱 |
| `POST /api/knowledge/ontology/read` | 读取知识库图谱 |
| `POST /api/knowledge/ontology/query` | 生成确定性查询计划 |
| `POST /api/knowledge/hybrid-search` | 执行原始与本体增强的混合检索 |
| `POST /api/knowledge/ontology/candidates/extract` | 从选定文档切片调用应用模型生成带证据的待审核候选 |

混合检索返回 `query/plan/strategy/results`。`strategy` 为 `vector-only` 或 `ontology-enhanced`，用于调试与评测，不表示答案可信度。

查询计划接受受控约束（实体类型、关系、属性、遍历方向和结果上限），运行时最多执行两跳遍历并返回明确的节点/边路径。自然语言中直接出现的实体名称、别名、实体类型、属性值和关系谓词可形成确定性匹配信号；服务端不会执行模型自由生成的 SQL 或 SPARQL。

混合召回保留三条路径：原始问题向量召回、本体扩展词向量召回、正式图谱 `documentId/chunkId` 绑定的证据切片定向召回。三路结果按知识库和切片 ID 去重、加权排序，并在响应中返回 `retrievalRoutes` 便于调试。证据切片不可读取时仅丢弃该路径，不阻断原始向量召回。

## 模块边界

- 公共 Schema：`@workexpert/contracts`；
- 图谱存储、查询规划和检索融合：`@workexpert/agent-core`；
- HTTP 路由：`apps/api`；
- API 负责写入，renderer 不直接访问文件；
- 候选抽取可调用应用模型，但模型只能输出待审核候选，且证据引用必须属于本次授权的文档切片；查询规划仍不调用大模型，保证可复现和可测试。
- 自动抽取按完整知识切片分批调用模型（当前最多 2 片/约 4500 字符），先根据用户分析重点和业务概念密度稳定排序。Qwen 与本地模型最多 2 路并发，其他云模型最多 4 路；单次请求 90 秒硬超时，超时批次降为单切片顺序续跑一次，结构化响应不完整时最多缩小一次范围。单个密集切片缩小时只改变模型分析上下文，持久化切片及证据 ID 不变。严格 Schema 不受兼容端支持时记录模型能力，后续批次直接使用 JSON 对象约束，避免重复失败。相同模型、指令和切片组合可复用有界进程内缓存；首批候选立即保存，后续候选合并写入。任务检查点同时保存成功与失败切片，即使零候选或全部失败也返回可续跑结果，仅重新提交未完成切片。

## 安全与降级

- `archived` 节点和关系不参与召回；
- 图谱命中只加权，不作为绕过权限的依据；
- 图谱为空、损坏或无命中时，返回空计划并保留原始向量路径；
- 后续权限过滤采用“用户权限 ∩ 数字员工权限 ∩ 项目权限”。

## 五步治理工作台

数据按 `AI 原始输出 → 候选工作区 → 人工审核草稿 → 待发布变更集 → 正式版本` 单向推进。后台抽取任务由 API 进程托管，Renderer 仅保存任务 ID 并轮询，页面关闭不取消任务。候选操作写入 SQLite 工作流表；暂存将已接受候选合入草稿，发布前通过结构和证据校验；每次发布写入不可变版本快照，回滚读取旧快照并创建新的反向版本。

## 图谱治理命令层

图谱审核不直接写表。规则扫描和应用模型均只生成白名单治理命令（合并、重命名、变更类型、删除节点/关系、反转关系），API 在单事务内把命令应用到草稿并保存操作前后快照。AI 建议必须经过契约校验和人工接受；撤销读取最近一次未撤销操作的前置快照。正式版本与候选证据不由 AI 直接修改。
# ONT-27 增量审核

ONT-29：API 为运行中任务持有不序列化的 OntologyExtractionControl；每个模型批次拥有独立 AbortController，以任务内唯一 batchNumber 定位，过期控制请求返回 409。模型调用与重试均使用批次信号，取消竞速会拒绝迟到输出；跳过只影响当前批次，停止影响所有当前请求及未启动队列。已成功并进入保存阶段的批次不再可跳过，停止会等待其保存完成。用户跳过/停止不计入服务熔断，结果统一保留未完成切片并按 partial 返回。

新 /analysis/skip 与 /analysis/stop 接口使用现有知识库所有权检查；stopRequested、skippedChunkIds 和 skipped 批次状态为兼容性新增字段，旧任务记录无需迁移。停止完成后进入检查步骤；候选不会自动通过审核或发布，无草稿时呈现审核/继续分析入口并禁止发布。

每批候选与成功检查点在 ontology.sqlite 同一事务写入后，才向任务状态暴露 candidateIds/completedChunkIds。检查点键使用输入内容、模型、服务地址、分析重点与强度的哈希，不包含密钥；成功空结果同样记录，审核状态在重放时保留。弹窗固定任务候选快照，后续批次不改变当前审核范围。入草稿支持显式 candidateIds，关系端点缺失时拒绝；发布仅将 staged 候选标为 committed。任务完成读取最新 workflow，不回写旧结果快照。

工作台采用四步导航，页面查看位置与实际构建进度分别记录；分析和候选管理共用第二步，检查与发布确认共用第三步，召回验证独立第四步。恢复时从服务端任务、候选状态及草稿变更推导进度，不以用户点击导航作为完成依据。发布预览请求 draftOnly=true 时只读取实际草稿，并执行发布所用的结构及已确认模型规则校验；旧请求默认为 false，继续支持接受候选的模拟预览。该参数不改变持久化结构。
